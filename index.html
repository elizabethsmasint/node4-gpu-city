THE CONTRACT

Evidence you can inspect.

Read the data flow

The main workbench shows the selected kernel and its immediate neighbors on the same stream. Each row separates DRAM input, GPU working tile, and DRAM output. Only the selected row animates an illustrative transfer cycle; neighboring rows are static until selected. State badges and execution percentages use the recorded clock. Follow playhead selects the active kernel as the trace plays; selecting a row pins it without changing the clock. The independent transfer preview can be paused. Fill operations prepare a scalar without reading an input tensor. Unknown transfer patterns stay unknown.

Factory view

The default Waiting chain arranges individual launches in stream order: last finished, running now, next, and then. Choose a device/stream to inspect. Amber cards identify submitted kernels waiting for an earlier kernel on that stream to finish. Upcoming launches are distinguished from submitted work using the correlated host API. These arrows establish execution order, not tensor handoffs or the sole cause of a delay; recorded copies, event waits, and other work may also intervene. Full city renders each launch as a workshop. Filters retain earlier kernels as context. Select Activity to return to grouped workshops or the 48 SM scene.

In Activity layout, Overview groups repeated launches into at most four illustrated workshops, ranked by summed kernel time within the displayed window. Buttons below include every matching operation family and its launch count. Workshops are operation families, not physical SMs. Full city shows the GPU district. Each factory represents an SM; crews represent thread blocks, and 32 worker figures illustrate a warp. The crates beside factories represent shared memory. Orders leave dispatch, materials move between global-memory warehousing and the L2 distribution center, and machinery illustrates computation. All placement and routing are educational.

Directly recorded

CUDA implementation names, event timestamps and durations, streams, grid and block dimensions, shared memory and registers where exported. Nsight kernel groups retain the mangled implementation and all launch dimensions. CUDA memcpy and memset records retain their byte counts.

Source-attributed or sampled

The historical PyTorch trace provides operator names, input shapes and scalar arguments. These are joined to GPU events within that trace only. Fresh Nsight add/fill source context comes from matching historical families, not a cross-run event join. NCU L2 bytes describe a separate representative replay sample matched by full signature and configuration.

Illustrative

SM placement, worker counts and motion, work-crew assignment, warp grouping, machinery, cache paths and the tensor values in the operation viewer. The city is an explanatory animation, not measured occupancy, a physical floor plan, or a transaction-level simulation.

Unknown stays unknown

Nsight captures contain no model phase annotations, tensor pointers or per-warp stalls. Nearby events are not proven data dependencies. Gaps mean no captured kernels or memory activities, not proof that the entire GPU was idle.

Timing rules

Playback speeds are real multipliers of trace time. Waiting chain always uses the exact cursor, and speeds of 0.0001× or slower also use exact activity. At full-step scale, Activity Overview summarizes up to 100 ms of trailing activity to make repeated work readable. Full city uses a shorter interval proportional to the visible timeline. Summary durations are clipped to that interval; overlapping kernel time is summed, not treated as occupancy. Zoom in to see exact activity at the cursor. Educational computation loops and the GPU/DRAM box fills share their own slow-motion clock. Box percentages describe a representative tile transfer, not measured memory traffic, capacity, or a portion of the recorded kernel duration. GPU means the working tile; DRAM shows output writes. Fill kernels prepare a scalar and write without an input-tensor load. Unrecovered kernels show an unavailable transfer pattern. The inspector dependency chain follows the selected launch independently of the cursor, with links only between non-overlapping adjacent kernels in a known device/stream. Filtering hides records but never compresses time.

DATASETS & REPRODUCTION

Built from your captures.

Load another capture

The app uses plain JavaScript and Canvas, served by Python’s standard library. Convert an Nsight SQLite export, .nsys-rep, or PyTorch Chrome JSON trace:

python3 gpu_city/normalize.py convert trace.sqlite \
  --output /tmp/replay.json --sync-pair 0 1

Then use Load a trace to open the normalized JSON. Ambiguous Nsight captures require explicit boundaries so warmup is never silently included. PyTorch JSON timestamps are interpreted in microseconds, regardless of displayTimeUnit.

Bring your own execution trace
Open a normalized GPU City JSON file. Existing traces can be converted locally without accessing the GPU:
python3 gpu_city/normalize.py convert capture.sqlite \
  --output /tmp/replay.json --sync-pair 0 1

python3 gpu_city/normalize.py convert trace.json \
  --output /tmp/replay.json
For .nsys-rep, the converter uses an installed nsys export. Explicit Nsight synchronization pairs use zero-based indices. PyTorch imports default to the complete recorded GPU span; use interval bounds to isolate a step.
